# 业务服务实现与测试

本文件说明认证、账号管理和校园卡业务层的当前行为、错误语义及交接边界。公共接口以 [services](../include/services/) 下的头文件为准，存储读写契约见 [存储格式与查询契约](storage-schema.md)。

## 会话与公共校验

业务服务的 `actor` 参数只能来自成功登录后保存的 `Account` 会话快照。每个接口都会重新校验会话模型的字段格式和角色，不依赖菜单隐藏或调用方自报权限。返回成功前不会覆盖调用方的模型、列表或标量输出；失败时保持原值。列表接口要求调用方先初始化为空，失败时会清理已经构造的部分结果。

业务层按字节校验：

- 用户名长度为 1–48 字节，仅允许 ASCII 字母、数字、下划线、连字符和点。
- 密码长度为 8–64 字节；服务只把明文传给密码派生接口，不保存或输出明文。
- 学号固定为九位 ASCII 数字。
- 姓名、院系和班级是非空合法 UTF-8，并遵守公共头文件给出的字节上限。
- 性别仅允许“男”“女”“其他”；电话可为空，非空时仅允许 ASCII 数字、加号、连字符和空格。
- 金额始终是正整数分；余额必须非负，状态只能是正常或冻结。

参数为空返回 `APP_ERR_INVALID_ARGUMENT`。已通过会话校验但角色不允许操作时返回 `APP_ERR_PERMISSION_DENIED`。业务层发现已加载模型损坏时返回 `APP_ERR_INVALID_DATA`，不把损坏记录视为不存在或零余额。

## 认证服务

`auth_needs_bootstrap` 通过有效账号计数判断是否需要创建首个管理员。账号计数失败原样传播，不能把损坏账号目录当作空目录。

`auth_bootstrap_admin` 只在账号数量为零且目标用户名尚不存在时创建管理员。用户名或新密码格式错误返回 `APP_ERR_INVALID_ARGUMENT`；已有账号返回 `APP_ERR_ALREADY_EXISTS`。随机盐和密码派生值通过统一密码接口生成。

`auth_login` 对不存在用户名、错误密码和格式不合法的登录输入统一返回 `APP_ERR_AUTH_FAILED`。存储损坏、文件读写失败和密码派生内部错误原样传播。只有密码验证成功后才写会话输出。

`auth_change_password` 重新读取当前账号并验证旧密码。旧密码长度不合法或校验失败返回 `APP_ERR_AUTH_FAILED`，新密码长度不合法返回 `APP_ERR_INVALID_ARGUMENT`。每次成功修改都生成新盐和派生值；保存失败不声称修改成功，当前会话的账号标识和角色不变化。

## 账号服务

账号管理接口仅允许管理员调用：

- `account_create` 先校验用户名、密码、角色和关联学号约束，再检查用户名是否重复。卡用户必须关联已存在且合法的校园卡主记录；管理员和卡业务员必须传入空关联学号。
- `account_get` 通过用户名读取账号，并在返回前再次验证模型和路径主键。
- `account_list` 把有效账号复制到调用方列表，逐项验证后返回；任一失败都会清理结果。
- `account_delete` 禁止管理员删除当前登录账号。删除其他账号只删除账号记录，不删除学生与校园卡主记录，也不提供最后一个管理员保护。

创建账号成功后，密码盐和派生值只存在于账号模型与存储文件中；业务层不打印凭据。

## 校园卡服务

校园卡接口按角色执行：

- 卡业务员可以开卡、按学号或姓名查询、冻结和解冻。
- 卡用户只能查询和操作会话绑定的本人校园卡，不能通过参数指定其他学号。
- 管理员没有校园卡业务权限。

`card_issue` 校验全部学生资料后拒绝重复学号，并强制创建零余额、正常状态的主记录。保存主记录成功后才追加姓名索引；索引失败返回原始错误，但已经保存的主记录不回滚。

`card_get_by_id` 和 `card_find_by_name` 在返回前重新验证主记录。按姓名查询对索引候选项按原始 UTF-8 字节筛选，无命中返回成功空表；主记录损坏或存储错误不会被解释为无命中。查询和普通卡业务不触发全量索引维护。

`card_update_own_phone` 只修改会话绑定卡片的电话，允许空字符串，冻结卡仍可修改电话。电话不作为查询键，也不参与姓名索引。

充值遵守以下顺序：

1. 金额必须大于零。
2. 读取并验证本人主记录。
3. 冻结卡返回 `APP_ERR_CARD_FROZEN`。
4. 检查 `INT64_MAX` 加法溢出。
5. 保存成功后才写入新余额输出。

消费同样要求正金额和正常状态。金额大于余额返回 `APP_ERR_INSUFFICIENT_BALANCE`，只有保存成功后才写入新余额。字段校验、权限、冻结、余额不足和溢出失败都发生在写入前，不修改主记录。

`card_set_status` 只接受正常或冻结状态。状态原本相同时直接返回成功且不保存；其他情况下保存新状态，余额不变。

## 失败与持久化边界

业务服务不直接拼路径、不调用文件访问接口、不处理 JSON。存储层的 `APP_ERR_IO`、`APP_ERR_INVALID_DATA` 和 `APP_ERR_NO_MEMORY` 原样传播。

开卡涉及“主记录保存”和“姓名索引追加”两个文件操作。第二个操作失败时可能留下主记录，系统不提供跨文件事务或回滚。账号创建、密码修改、充值、消费和状态修改只在存储保存成功后报告成功。

## 测试设计

业务测试使用 [service_test_support.c](../tests/service_test_support.c) 中的内存存储替身，仅链接到测试目标，不进入正式程序。替身支持写入测试账号和主记录、统计存储调用次数，并为指定存储操作注入一次错误，以便验证：

- 三种角色的允许和禁止操作。
- 空参数、字段边界、非法 UTF-8 和枚举值。
- 重复用户名和学号、未开卡关联及删除自身账号。
- 冻结状态、零负金额、余额不足和加法溢出。
- 失败不写文件、输出保持原值、列表失败后为空。
- 存储错误传播，以及开卡主记录已保存但索引追加失败的边界。

运行业务测试：

```sh
ctest --test-dir cmake-build-debug \
  -R '^(auth_service|account_service|card_service)$' \
  --output-on-failure
```

这些测试证明业务规则在存储替身上的行为，不替代成员 A 的真实文件存储、路径和 JSON 测试。真实存储接入后，仍须使用独立临时数据目录完成联调和重启验证。

## 交接要求

成员 A 接入真实存储时，应保证账号和主记录只在成功时写入输出，列表失败时为空，损坏数据不被转成未找到或零值，并保持 `card_issue` 的“主记录先于索引”调用顺序。

成员 C 接入 CLI 时，应从成功登录结果取得 `actor`，只使用业务服务返回码生成用户提示，不在界面重复实现角色、余额、冻结或密码规则。存储和服务实现全部接入后，再开启 `CAMP_CARD_BACKEND_READY` 执行端到端测试。
